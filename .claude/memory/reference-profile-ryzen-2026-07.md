Fresh machine: **AMD Ryzen 5 4500U (Zen 2), 6 cores** — NOT the i9-13900HX of [[reference-pawnstar-perf-measurement]], so absolute nps differ. This machine's `go` needed a PATH fix (go 1.26 at /usr/local/go/bin ahead of distro go-1.22); C++ needs cmake+ninja (apt) and `perf` needs `sudo sysctl kernel.perf_event_paranoid=1`.

**Method:** both engines `bench` (single-thread, book-off, identical **6,888,983-node** tree — C++ build 610 has butterfly history too, so trees match bit-for-bit). `perf record -F 1999 -g --call-graph fp` on each native binary (same tool both sides = apples-to-apples, unlike pprof-vs-callgrind). C++ built `make RELEASE=1` (-O3 -g, DEBUGX off).

**Speed:** C++ ~1.19M nps vs Go ~0.78M nps = **Go 1.53× slower** (stable across 3 interleaved rounds; cf. ~1.66× on the old i9). Eval-dominated as always.

**Profile shapes are very similar** (eval ~55-60% both sides). Near-parity relative cost: move ordering (C++ 7.2% / Go 7.1%), SEE (~5.8% both), alpha-beta (4.3/5.0). The output-layer forward pass is at parity-or-better for Go — the hand-written AVX2 `outputDotInt8Asm` (18.2% self) does its job; C++ inlines its dot into EvaluatePosition (28.3% self incl. dot).

**Two Go-specific costs stand out:**
1. **`nnueBoard()` conversion ≈ 8-12% of total runtime — the standout lever, no C++ equivalent. FIXED 2026-07-03, +~10% nps, via zero-copy reinterpret.** Was: Go's `currentAccumulator` 20.2% self (vs C++ CurrentAccumulator 1.3% + memmove 15%). Only ~21% of that was the 4KB `accStack[j]=accStack[j-1]` copy (`rep movsq`, *cheaper* than C++'s `__memmove_avx_unaligned_erms`); the rest was two full `nnueBoard()` builds (from+to) per eval — a 64-iteration `squares` type-converting byte-loop + 9 bitboards materialized into `nnue.Board`. C++ pays nothing: it hands `Update`/`DiffSide` a `Position const&` and reads it in place. **Root cause was the *materialisation*, NOT the package boundary.** The winning fix (user chose this over an intermediate `boardStack` cache and over merging the packages): `position`'s first three fields (`pieces [7]bitboard`, `colors [2]bitboard`, `squares [64]piece`) are already byte-identical in layout to `nnue.Board` (`bitboard`=uint64, `piece`=uint8, same order — mirrors C++ `Position`), so `nnueBoard()` became `(*nnue.Board)(unsafe.Pointer(pos))` — a zero-copy pointer view. `currentAccumulator` passes posStack entries straight in; **`boardStack`/`deriveNnueBoard` deleted** (less code than before). Package stays import-free (the unsafe cast lives in nnue_bridge.go). Guard: **`TestNnueBoardLayout`** (offsets + random-position round-trip vs the retained explicit builder `nnueBoardExplicit`) fails loudly on any field reorder. Net +~10% interleaved (778k→863k nps), bench bit-identical (6,888,983), all gates + `-race` green. No SPRT needed (search unchanged); would only confirm ~+5-8 Elo. **Waypoints (rejected en route):** derive-alone (incremental child board, keep boundary) gave only +2% — the per-child *parent* rebuild was the real cost, not the child build; a `boardStack` cache of converted boards got +9% but the reinterpret is simpler and fully C++-parity. Files: engine/nnue_bridge.go, engine/search.go, engine/nnue_test.go (guard), CLAUDE.md.
2. Move generation codegen gap: Go movegen+pins ~7.3% vs C++ 4 GenMoves templates 5.2% — the known, largely-unrecoverable compiler gap (bounds checks/inlining), not algorithmic ([[reference-pawnstar-perf-measurement]] PEXT-is-dead).

**Re-profile after the zero-copy fix (pprof of committed code, BenchmarkSearchProfile depth 12):** currentAccumulator self collapsed 20%→5.5% (conversion gone; cum 34% is the Update it calls). New top self: outputDotInt8Asm 15.4% (maxed — AVX2 asm, Zen2 no AVX512), **transpositionTable.find 15.3%** (memory-latency bound), addColumn+subColumn ~16.7% (Load/StoreSlice alone 7.7%), sortMoves 3.2%, evalHashTable.find 3.0%. **TT prefetch DONE (committed after zero-copy), +~2% nps:** C++ prefetches the child TT cell after MakeMove (search_state.h:415, `__builtin_prefetch(addr,0,1)`); Go had none — a parity gap. Added `prefetchAddr` (PREFETCHT2 amd64 / PRFM PLDL3KEEP arm64 / no-op scalar, engine/prefetch_*.{go,s}) + `tt.prefetch(hash)`, called in searchSingleMove right after playMove. Result-neutral (bench bit-identical 6,888,983), +2.0% interleaved (858k→875k). Per-node asm-call overhead caps it at the low end of the 2-5% range. **Dead gives-check computation removed (committed after prefetch), +~3% nps.** The move gives-check flag (bit 22) was set only on non-quiet moves (scoreAndSortMoves capture branch) but read only in the LMP guard, itself gated on isQuiet() — so `!isChecking()` was vacuous (always true when reached). The `seeAttackersTo(enemyKing)` scan computing it ran for every capture in move ordering = pure dead work. Dropped SEE's bool return + seeAttackersTo + the vacuous LMP term + move.withCheck/isChecking. Bench bit-identical (6,888,983); C++ has the identical vacuous flag so parity holds. **Latent shared gap → a STRENGTH experiment candidate: quiet checking moves are NOT exempt from LMP in either engine (the flag only ever guarded captures, which LMP skips anyway). Actually exempting quiet checks from LMP needs check detection for quiet moves + SPRT (and a matching C++ change to keep parity).**

**Fused accumulator update: TRIED, REJECTED — both variants neutral (~0%), reverted.** Hypothesis was that Update's ~28% cum (addColumn 9.4 + subColumn 6.5 + the `accStack[j]=accStack[j-1]` copy ~5 + Load/StoreSlice 8.2) had ~5-8% recoverable by cutting accumulator dst traffic. (a) **Full single-pass** `UpdateFrom` (dst = src − subs + adds via shape-dispatched fusedSubAdd/fusedSub2Add/fusedSub2Add2 kernels): **+0.3% = noise.** Re-profile showed the fused kernels (fusedSub2Add 11% + fusedSubAdd 8.9% ≈ 20%) cost MORE than the old addColumn+subColumn (~16%) — longer serialized dep chain + the collect/dispatch overhead — cancelling the copy saving. (b) **Copy-fold only** (`subFrom(dst,src,col)` = dst=src−col seeds the first sub, keep tight addColumn/subColumn for the rest): **−0.5% = noise.** **Root cause: the accumulator update is bound by the FEATURE-COLUMN loads (cache-missing reads from the 6 MB weight table, one per changed feature — irreducible, identical in every variant), NOT the dst load/store (L1-resident) or the copy (rep movsq from L1, already cheap). So there is no dst-traffic win to get.** Do not re-attempt on similar hardware. Bug found en route (guard if revisited): the no-placement-change case (NULL MOVE — currentAccumulator catches up through null-move plies) needs dst=src seeding, which the copy did implicitly; TestNNUEIncremental does NOT cover null-move accumulator catch-up (add such a case if you touch this). Also surprising in that profile: **prefetchAddr self = 5.6%** (per-node ABI0 call overhead ~40ns/call); making it ABIInternal could recover some and improve the prefetch's net +2%. Also possible: prefetch the eval cache (C++ doesn't, net-new).
