# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build

Requires Go 1.26.x - not 1.27 or later: the amd64 NNUE SIMD kernels use the experimental `simd/archsimd` package, gated behind `GOEXPERIMENT=simd`, and 1.27 changed its API (`LoadInt16x16Slice` became `LoadInt16x16`, `StoreSlice` became `Store`, the array forms gained an `Array` suffix), so the code does not compile there. arm64 uses hand-written NEON assembly instead, which needs no experiment. The newest gopls needs Go 1.27 to build, but `go install` fetches that toolchain into the module cache for gopls's own build and leaves the repo's Go at 1.26.

**Setting up a machine.** `tools/setup-dev.ps1` (Windows) and `tools/setup-dev.sh` (Linux, macOS) install what
building, testing, linting and debugging need - Go, the newest 1.26.x (1.27 changed the `simd/archsimd` API the amd64
kernels use), golangci-lint of CI's v2.12 line, gopls and dlv for VS Code's Go extension, and a C compiler for the race
detector (build-essential, Xcode's command-line tools, or on Windows MSYS2's CLANG64 clang, which `go env -w CC` points
cgo at) - plus the git hooks and the recommended VS Code extensions, checking each first, so they are safe to run again;
`-Check` / `--check` only reports. In VS Code they are the `setup environment` and `check environment` tasks. On
Windows, run the Makefile from Git Bash with `mingw32-make`, MSYS2's native make, which the script installs: MSYS2's
own `make` is handed only the PATH when Git Bash starts it, and leaves Go without a temporary folder.

```bash
make build                  # build with GOEXPERIMENT=simd (recommended) -> ./pawnstar-go
make test                   # run all tests with SIMD enabled
make test-short             # -short variant
make cover                  # the whole suite's statement coverage -> coverage.out; fails under COVER_MIN (90 %)
make baseline               # snapshot the current binary as ./pawnstar-go-baseline for SPRT
```

`make build` names the binary `pawnstar-go_MAJOR_MINOR_BUILD` with `pawnstar-go` beside it, each with `go env GOEXE`'s
suffix (`.exe` on Windows); `pawnstar-go` is a symlink on Linux and macOS and a copy on Windows, and the build deletes
any other versioned binary it finds. `make race` switches cgo on itself (`-race` needs it); its C compiler is go's `CC`,
which on Windows is the MSYS2 clang the setup script records with `go env -w`. `make cover` runs the full suite
instrumented (`-coverpkg=./...`, so a package's tests count for the code they reach in another; the default `set` mode,
since `atomic` slows it far more than it is worth) under a 45-minute timeout, and leaves `coverage.out` (git-ignored)
for `go tool cover -html=coverage.out`. The total is gated at `COVER_MIN` (90 %, a variable in the `Makefile` and the
one place the number is written): under it `make cover` fails, and so does CI's `coverage` job, which runs it. The
gated figure is `./...` whole - the engine, `engine/nnue` and the binary's `main` - since the repository has no Go
developer tool a release does not ship (`tools/` holds shell and PowerShell scripts); test files are never counted.
It stands near 99 %: the UCI dispatcher, the `go` parser, `setoption`, `bench` and `main` itself are driven in process
(`engine/uci_inprocess_test.go`, `main_test.go`), since the subprocess UCI test is invisible to the profile. A new
feature brings its tests with it rather than spending the margin.

The `Makefile` sets `GOEXPERIMENT=simd` for you. Building directly still works — `GOEXPERIMENT=simd go build -o pawnstar-go .` — and a plain `go build` compiles too. The NNUE kernels are build-tag split three ways, all **bit-identical**: **amd64 + `goexperiment.simd`** → archsimd + hand-written AVX2 asm (the Makefile default); **arm64** → hand-written NEON asm (no experiment needed); **anything else** (plain amd64 `go build`, other arches) → scalar fallback. SIMD/NEON is roughly an order of magnitude faster than scalar on the hot paths (int8 output dot ~9.9× on Apple Silicon; accumulator update ~7×).

Run the engine interactively via UCI: `./pawnstar-go`. NNUE is the only evaluator (the embedded net is installed at construction); load an alternative net with the `EvalFile` UCI option.

**Versions and releases** (README, "Versions and releases"): the version is `MAJOR.MINOR.BUILD` from git alone - the nearest annotated `vMAJOR.MINOR` tag and the commits since it (`tools/version.sh`), linked in by the `Makefile` as `-X pawnstar-go/engine.version=...`; a plain `go build` reports 0.0.0. Nothing in the tree is edited to release. Pushing a mark (`v1.1`) runs `.github/workflows/release.yml`: built and tested on Linux, Windows and Apple silicon, the Windows binary eSigner-signed (publishing runs only - each signing spends the allowance), the macOS one Developer ID-signed and notarised in a zip, published as `v1.1.0`. `gh workflow run release.yml --ref <branch> -f dry_run=true` proves a change to it without publishing or spending a Windows signing. **A release publishes no source tarball** (removed 2026-10-30, together with `make source-archive` and CI's `pawnstar-go-source` artifact): the repository is public, so the source is a clone or a fork, and the four assets are the three binaries plus `-docs.zip`. The documentation bundle carries `THIRD-PARTY-NOTICES.md` as well as the two markdown documents.

## Running Tests

Move generation correctness is verified by perft tests against known node counts:

```bash
go test ./engine/ -run TestPerft -v               # all perft positions, capped at depth 5 (~12s); node counts >= 1e9 removed
go test ./engine/ -run TestPerft -short -v        # same depth-5 cap (short no longer differs)
go test ./engine/ -run TestPerft/002 -v           # single position by 1-based index (002 = second position)
go test ./engine/ -run TestPerftExtra -short -v  # verify incremental Zobrist hash vs recomputed hash at every node
go test ./engine/ -run TestSearch -short -v       # run search on every EPD position to depth 9
go test ./engine/ -run TestBratkoKopec -v         # 24 Bratko-Kopec positions at depth 8; search quality regression
go test ./engine/ -run TestSEE -v                 # 24 SEE unit cases + TestSEECrossCheck (fast == make-move reference over ~1M captures)
go test ./engine/ -run TestNNUEReference -v       # NNUE int16 EvaluateExact vs 250-FEN C++ reference (gate: 0 cp)
go test ./engine/ -run TestNNUEInt8 -v            # search's int8 eval within 40 cp of int16 ref (also scalar==SIMD)
go test ./engine/ -run TestNNUEIncremental -v     # lazy accumulator == full refresh, bit-identical
go test ./engine/ -run 'TestOpeningBook|TestShippedBookProvenance' -v  # book '?' handling, and the embedded book's provenance
go test ./engine/ -run 'TestArmDeadline|TestTimeControl' -v  # chess-clock deadline / defaults
make test-uci                                     # UCI protocol as a process: handshake, seldepth, searchmoves, currmove, bench determinism + the golden signature
make race                                         # concurrency tests (Lazy SMP, ponder clock) under the race detector
go test ./engine/ -bench BenchmarkNNUE -benchmem   # NNUE evaluate/refresh/update micro-benchmarks
go test ./engine/ -bench BenchmarkPerft7 -benchtime=10s
```

Run these with `GOEXPERIMENT=simd` (or via `make test`) so the SIMD kernels are exercised. `make check` is the full gate, and it is exactly `test` (the whole suite) plus `race`. The focused targets — perft, SEE, Bratko-Kopec, the NNUE gates, the opening book, Lazy SMP, chess-clock timing, the UCI protocol test — are deliberately **not** prerequisites: each is a strict subset of `test` with verbose output, and as prerequisites of a `make -j` build they meant ten concurrent `go test` processes fighting over the runner's cores. They remain standalone for diagnosing one invariant. `test` covers the UCI protocol test, whose `TestUCIBenchDeterminism` also asserts the **golden bench signature** (`benchGoldenNodes` = 5,617,906, the shipped v20 net at the default shape; it was 6,601,454 with the v12 net at v12's shape): bump that constant only for a deliberate, SPRT-gated engine change, never to quieten the test. The dependency on `test` is load-bearing: the focused targets are a union of `-run` regexes, so on their own they **silently skip** anything they do not match, and two load-bearing gates were being skipped that way — `TestNnueBoardLayout` (the hard contract guarding the unsafe `position`→`nnue.Board` reinterpret) and `TestOutputDotInt8Asm` (the AVX2/NEON dot bit-identity gate), because `-run TestNNUE` is case-sensitive and matches neither. Never gate solely on a `-run` regex union. CI additionally runs **golangci-lint** (see [.golangci.yml](.golangci.yml) — a deliberately conservative set; any lint fix touching engine code must be re-gated by `bench` == 5,617,906) and a **scalar-fallback job** that builds with `GOEXPERIMENT` cleared and asserts the same golden bench, which is what makes "the three kernel variants are bit-identical" a tested invariant rather than a claim. Always run `TestPerft` and `TestSearch` together when verifying engine changes. `TestBratkoKopec` is the search quality gate; it runs with **NNUE enabled** and its accepted move set was generated from multiple NNUE runs at depths 7–8 (regenerate with `GEN_BK=1 go test -run TestGenerateBratkoKopecNNUE` after swapping the embedded net — the committed set belongs to the shipped v20 net and was regenerated for it). `TestNNUEReference` (int16 exact-eval correctness), `TestNNUEInt8` (the search's int8 eval vs the int16 reference, and scalar == SIMD), and `TestNNUEIncremental` (lazy accumulator correctness) are the NNUE gates — all must stay green after any accumulator or kernel change.

Perft (move generation only) runs at ~200 Mnps single-threaded (start position) and is **core-count-independent** now that move generation is allocation-free (the stack `moveList`, above). It previously ran ~145 Mnps single-threaded and collapsed to ~45 Mnps under a multi-core `go test` (e.g. `make check`), because the per-node slice allocation made move-gen GC-bound and Go's concurrent collector then contended for memory bandwidth across cores — the allocation-free `moveList` fixed both. The NNUE eval used in real search is slower per node but far stronger (when first ported: SPRT +572 Elo vs the engine's former handcrafted eval at fixed depth, since removed). The C++ engine reaches ~540 Mnps on the same machine, so the raw move-gen gap is now ~2.7× (down from ~3.7× before this change); the gap is compiler codegen (inlining, bounds checks), not algorithmic — the C++ engine's PEXT sliding attacks measured little-to-no gain over magic bitboards in its own testing. Perft benchmarks are the primary tool for tracking move-generation performance regressions. In real NNUE search the Go↔C++ speed gap is far smaller than the raw move-gen gap, because search nps is dominated by evaluation (where the SIMD kernels are close to the C++ hot path): over the 24 Bratko-Kopec positions at depth 10, single-threaded with bit-identical trees, the Go engine runs ~1.06 Mnps against the C++ engine's ~1.77 Mnps — **~1.66× slower** (measured by interleaving the two engines per position across several rounds; stable 1.58–1.74). Those figures are the amd64 Linux machine. On **arm64 (Apple Silicon)**, after the NEON kernels (below), the gap is essentially **closed**: the 16-position `bench` (identical 7,007,401-node trees — the pre-butterfly signature — interleaved same-thermal-state) runs the Go engine at **~1.14 Mnps vs C++ ~1.15–1.19 Mnps — ~0.98× (parity, within 2–3%)**, up from ~190k nps (6.0× gain) when arm64 was fully scalar.

## SPRT self-play harness

`tools/sprt.sh <candidate-bin> <baseline-bin> [rounds]` runs a fastchess binary-vs-binary SPRT (single-core engines via `GOMAXPROCS=1`, fixed depth via `DEPTH=`, openings from `~/pawnstar_nnue/openings.epd`). ## Known Pitfalls

**Promotion notation** — `move.String()` outputs correct UCI notation (`e7e8q`). `move.GoString()` outputs a human-readable debug form (`pe7e8=q`) that is **not** UCI and must never be used for engine communication.

**`noSquare` equals a1** — `noSquare` is defined as `square(0)`, which is the same integer value as `a1`. It is only used for the en-passant target square and castling sentinel contexts where `a1` would never validly appear.

**`ucinewgame` does not clear the TT/eval cache** — `newGameFromFen` (called on `ucinewgame`) resets only the position stack, node count, cancel flag and clock; the transposition table and eval cache **persist** (only the `Clear Hash` button clears them, in `HandleCommand`). This is deliberate — you want the TT to carry across moves within a game — but it diverges from the C++ engine, which clears on `ucinewgame`. The consequence for tooling: repeating the *same* position via `ucinewgame` + `go depth N` in one persistent UCI session gives **non-deterministic, shrinking** node counts as the stale TT is reused. To reproduce the deterministic BK node counts in a persistent session, send `setoption name Clear Hash` before each search (or start a fresh process per position). The in-repo tests are unaffected — they build a fresh `Game` per position.

## Architecture

Pawnstar-Go is a UCI chess engine using bitboard board representation and alpha-beta search. It is a port of the C++ Pawnstar engine.

**Board representation** — `position` ([engine/position.go](engine/position.go)) is a value type used with copy-make traversal: `makeMove` and `makeNullMove` operate on a caller-owned copy of the struct. `Game.posStack []position` (heap-allocated, capacity 512) maintains the history stack; undoing a move is a slice truncation. The struct holds `pieces [7]bitboard` (indexed by piece type constant, `pawn`=1…`king`=6; index 0 (`noPiece`) holds the **occupied-squares** bitboard, maintained incrementally so `occupied()` is a plain load — mirrors the C++ `pieces_[kNone]`) and `colors [2]bitboard` (indexed by color constant, `white`=0/`black`=1) instead of named per-piece fields, plus a `squares [64]piece` array for O(1) lookup, an incremental Zobrist hash, `colorToMove color`, and `halfMove uint8` (50-move clock: reset by a pawn move or a capture, en passant included, and advanced by every other move - castling too, which is irreversible but neither, as FIDE Article 9.3 and FEN count it; `TestCastlingAdvancesFiftyMoveClock`). The king square is not stored; `kingSquare(c color) square` computes it on demand as `(pieces[king] & colors[c]).lsb()`. `positionFromFen` constructs a `position` from a FEN string and treats `'0'` as a no-op digit (advance by 0 squares) to handle non-standard FEN notation. `bitboard` ([engine/bitboard.go](engine/bitboard.go)) is a `uint64` with methods for all set operations.

**Move encoding** — `move` ([engine/move.go](engine/move.go)) is a packed `int64` with an identical bit layout to the C++ version:

```
bits  0– 5  to square
bits  6–11  from square
bits 12–14  moving piece
bits 15–17  captured piece
bits 18–21  move type
bit     22  reserved (formerly gives-check; no longer computed)
bits 23–24  transposition node type (nodeType)
bits 25–32  transposition depth searched (int8)
bits 33–40  transposition age / generation (uint8)
bits 41–63  score (signed 23-bit)
```

Bits 23–63 are dual-purpose: during move ordering they hold a sort score (`move.withScore`/`move.score`, bits 41–63), and inside a transposition entry they hold the packed `{score, depth, nodeType, age}` metadata (`move.withTTData`/`setTTAge` plus the `ttDepth`/`ttNodeType`/`ttAge` accessors). A move is never both at once, so the spare bits are shared — this is what lets a TT cell be exactly two 64-bit words (see the lockless table below). The score is signed 23-bit; every move-ordering score and stored search score fits. `move.bits()`/`moveFromBits` convert to/from the raw `uint64`. Move lists use a **stack-resident `moveList`** (a fixed `[256]move` array + `count`; [engine/movegen.go](engine/movegen.go)): the hot paths (`perft`, `searchAlphaBeta`, `searchQuiescent`) declare a local `var ml moveList` and call `generateLegalMovesInto`/`generateLegalCapturesInto`, so move generation is **allocation-free** (escape analysis keeps `ml` on the stack). Cold callers (UCI setup, opening book, tests) use the slice-returning `generateLegalMoves` wrapper, which copies into a right-sized heap slice. This replaced a per-node `make([]move, 0, 64)` that heap-allocated on every node. `move.equal`/`isNone` mask to the identity bits (0–21), so metadata never affects identity.

**Attack generation** — [engine/tables.go](engine/tables.go) initialises all precomputed data in its `init()` function: magic bitboard tables for sliding pieces (`bishopAttacks`, `rookAttacks` — magic numbers found offline with seed 1337), ray tables (eight directions × 64 squares), knight/king/pawn attack tables (plus empty-board bishop/rook attack tables used by pin detection), intervening-square tables, and Zobrist hashes (filled from a fixed-seed `xorshift*` PRNG, seed `0xAA55AA55AA55AA55`, shared bit-for-bit with the C++ engine). `computePins` ([engine/pins.go](engine/pins.go)) identifies absolutely pinned pieces and their allowed ray before move generation.

**Move generation** — [engine/movegen.go](engine/movegen.go) implements fully legal move generation. `generateLegalMovesInto` and `generateLegalCapturesInto` are the entry points (with `generateLegalMoves` as the slice-returning wrapper for cold callers). Internally, `generateMoves` builds the king's forbidden-square set (with X-ray attacks through the king), handles double-check early return, restricts non-king moves to checker capture or interposition in single check, applies pin constraints via `pins.allowedSquares`, generates castling, and generates all pawn move types inline (including en-passant with a horizontal discovered-check test).

**Search** — `Game` ([engine/game.go](engine/game.go)) owns the lockless transposition table and eval cache (shared by all threads), the chess clock, opening book, position history stack, the reusable main-thread `searchState` (`mainSearchState`, restored to exact fresh-construction state each `go` by `resetForSearch`; helpers always build fresh), and `threadCount` (Lazy SMP thread count; default 1, raised by `main()` from `PAWNSTAR_THREADS`/`NumCPU` or the UCI `Threads` option). `isCancelPending` is an `atomic.Bool`. `startThinking` launches the search on one goroutine (so UCI can still process `stop`); `stopThinking` stores `true` into `isCancelPending` then blocks on a `sync.WaitGroup`.

**Draws at a node** — `searchAlphaBeta` tests, at node entry and in this order, insufficient material, the fifty-move clock (`isDrawByFiftyMoves`, 100 plies) and repetition. **Checkmate takes precedence over the fifty-move draw** (FIDE 5.1.1; 9.6.2 says it of the 75-move rule): at a clock of 100 or more a side to move in check with no legal move is mated, `checkmatedScore + ply`, and only otherwise is the node a draw - so a mate delivered on the hundredth ply is found and played (`TestMateTakesPrecedenceOverFiftyMoves`). The C++ and Rust engines do the same, at the same point, so the trees stay identical. The static eval has no fifty-move test of its own.

**Windows binary** - no package uses cgo, so the engine imports `kernel32.dll` alone and needs no Visual C++ redistributable or MinGW runtime. `tools/windows-dependents.ps1` reads a binary's import and delay-load tables from the PE file itself (what `dumpbin /dependents` lists) and fails on any other DLL, a C or C++ runtime DLL above all; CI's Windows artifact job and the release's Windows build run it.

**Lazy SMP** (ported from the C++ engine): `searchRootNode` launches `threadCount − 1` helper goroutines and runs the main thread itself. Each thread runs `iterativeDeepen` — an independent iterative-deepening search of the whole root — with its **own `searchState`**; helpers get a private throwaway diagnostics struct and their own copy of the root move list. The **main thread (id 0) is authoritative**: it prints `info`, applies time management, and returns the move. Helper threads (id ≥ 1) stay silent and follow the Stockfish-style iteration-skip schedule (`lazySmpSkipSize`/`lazySmpSkipPhase`) so they desynchronise and prefill the shared TT with diverse entries. When the main thread finishes it sets `isCancelPending` and joins the helpers.

The search is split by layer: per-thread state + the shared `searchSingleMove` wrapper in [engine/search.go](engine/search.go), the root driver + Lazy SMP + iterative deepening in [engine/searchroot.go](engine/searchroot.go), the main recursion in [engine/searchalphabeta.go](engine/searchalphabeta.go), and the capture resolver in [engine/searchquiescent.go](engine/searchquiescent.go). All recursive search functions take `*searchState`. **Everything on `searchState` is per-thread** — `posStack`, `hashStack`, `killers`, `history` (moved off `Game` so threads don't contend), continuation history, countermoves, the NNUE accumulator stack, `nodeCount`, and the `dbg *debugX` (the global `dbgx` for the main thread, a throwaway per helper). Only the lockless TT + eval cache, the read-only time control, and the atomic cancel flag are shared, so the concurrent search is data-race free with no locks. `newSearchStateFromGame` builds `hashStack` from the full game history and seeds `posStack` with the current position.

`searchRootNode` drives iterative deepening from `startDepth` (3). Each depth iteration is a single **full-window** root pass (`[initialAlpha, initialBeta]`): `alpha` starts at the minimum and is raised as root moves improve, so PVS null-windows every move after the first — there is **no aspiration window** (the C++ engine tested and rejected aspiration; a cross-engine BK diff at fixed depth confirmed aspiration was the largest Go↔C++ divergence, so Go dropped it to match). With aspiration removed plus Zobrist parity (shared `xorshift64star`), score-scale parity (§ Evaluation below), the per-move null-window fix (§ `searchAlphaBeta` below), and the PV-capture fix (§ Principal variation below), **all 24 Bratko-Kopec positions match the C++ engine bit-for-bit at fixed depth — identical bestmove, score, cumulative node count, and full principal variation** (single-threaded, book off; verified at depth 8 and depth 10). This is the standing faithfulness gate. Early-exit heuristics apply on the Standard clock when the best move and/or score are stable across depths.

`searchAlphaBeta` implements PVS plus the pruning/reduction stack ported from the C++ Pawnstar (margins in [engine/constants.go](engine/constants.go); they carry over because the NNUE eval is the same centipawn scale): internal iterative reduction (−1 ply when there is no TT move at depth ≥ `noTTReduceMinDepth`), and — at non-PV non-check nodes, using a static eval computed once — reverse futility pruning (`eval − rfpMargin·depth ≥ beta`) and null-move pruning (R=4, gated on `eval ≥ beta`). In the move loop: late move pruning (skip quiet moves once `moveIdx ≥ lmpBase + depth²` at depth ≤ `lmpMaxDepth`) and LMR (any late move at null-window non-check nodes: −1 at idx > 3, −2 at idx > 6 & depth > 3, −3 at idx > 12), re-searched at full depth on a fail-high. The **null-window predicate (`beta == alpha+1`) is recomputed per move against the current alpha, not precomputed once** — at a PV node, once an earlier move raises alpha to `beta−1` the remaining moves are effectively a null-window search and LMP/LMR must engage for them; this mirrors the C++ inline check and is required for bit-identical search (a precomputed flag left the last two BK positions diverging). Quiescence adds SEE pruning (stop at the first losing capture). A node in check is extended one ply (check extension) and its evasions are searched; quiescence re-enters `searchAlphaBeta` when in check. The pruning/reduction stack was worth +183 Elo (SPRT, 10+0.1); the check extension plus the countermove/continuation-history move ordering a further +160 Elo; the butterfly history table a further ~+7 (2026-07, consistent at 10+0.1 and 12+0.12, probe −17.7% fixed-depth nodes); Lazy SMP adds parallel scaling on top (4 threads ≈ +160 Elo vs 1 at 10+0.1).

**Principal variation** — the PV (a `variation` = `[]move`) is captured **at the moment a move raises alpha** and nowhere else: `copyVariation(parentPV, pv, move)` sets `parentPV = move ++ child.pv` both in the TT-move block and in the main move loop. There is deliberately **no post-loop re-copy** — after the best move, later siblings run `pv.clear()` then fail low, so by the end of the loop `pv` no longer holds the best move's line; re-copying there (an earlier Go bug) truncated the PV to ~2 plies. Removing that re-copy and adding the missing TT-move capture makes the full PV bit-identical to C++ (matches `SearchState::SearchAlphaBeta`, whose end-of-loop comment notes "parent_pv was already set … at the alpha-raise above"). `iterativeDeepen` captures the root PV the same way and publishes `ponderMove` = PV[1].

Move ordering (`searchState.scoreAndSortMoves` in [engine/moveorder.go](engine/moveorder.go), a banded scheme ported from the C++ `ScoreAndSortMoves`): (1) TT move tried first; (2) remaining moves scored into disjoint bands — winning captures/promotions `winningCaptureBase + SEE` on top, then the two killers, then the countermove to the previous move (`countermoveScore`), then quiet moves by `history + continuationHistory` clamped to `maxQuietScore`; losing captures score by their negative SEE and sink below the quiet moves. `prevMove` (the move played at the parent) keys the countermove and continuation-history heuristics. On a good move, `recordGood` credits the main history and continuation history with a depth-weighted gravity bonus; a beta cutoff additionally debits every *other* quiet move tried at the node (the malus — see the History heuristic section) and, for a quiet cutoff move, updates killers (`updateKillers`, now all quiet moves) and the countermove. The countermove table (`[contKeys]move`, keyed by `prevMove.pieceTo()`) and the 1-ply continuation history (`[]int16`, keyed by `[prev.pieceTo()][move.pieceTo()]`, gravity-updated) live on `searchState` and persist across a search. Sorting is `sortMoves` — a **stable in-place insertion sort** by descending score, used at every node and the root (mirrors the C++ `SortMoves`); a move list is small and hard-bounded, so insertion sort beats an O(n log n) sort with a scratch buffer, and stability makes equal-score move choices deterministic.

**Transposition table** — Single table ([engine/transposition.go](engine/transposition.go)), sized from `hashTableMB` (**64 MB**, matching the C++ `kHashtableMegabytes` and the Rust `HASHTABLE_MEGABYTES`; it was 512 here from `cec14a4` — a TT *locking* change that moved it as a side effect — until 2026-10-27, which silently broke the three ports' bit-exactness at every `go` while `bench`, pinned to 64 in all three, went on reporting parity) and rounded up to a power of two so entries index with `hash & mask`. **Lockless via Hyatt's XOR trick** (ported from the C++ engine): each 16-byte cell is two `atomic.Uint64` words — `data` (the packed move, carrying score/depth/nodeType/age in its spare bits) and `key = hash ^ data`. `find` loads both words with relaxed atomics and accepts the cell only when `key ^ data == hash`; a torn pair left by two concurrent stores (key from one, data from another) fails that check and reads as a miss, and the same reconstruction doubles as the full-hash collision guard. So there are no per-entry locks: workers read/write freely, racing writers resolve to a benign last-writer-wins, and a torn read costs at most a spurious miss (re-search) — never a wrong move or garbage score. Per-word atomicity keeps each word itself tear-free (and the race detector quiet); the XOR key supplies the cross-word consistency. Replacement policy (in `record`): overwrite when the slot is empty, the existing entry is from an older generation (`cur.ttAge() != currentAge`), the new depth is ≥ the stored depth, or the new node is PV. `age()` bumps `currentAge` (O(1), wraps at 256) at the start of each root search; `record` stamps it via `setTTAge`. The `transposition` value returned by `find` is `{hash, move}` with `depth()`/`nodeType()` accessors (and the score read via `move.score()`) straight out of the packed move. `searchSingleMove` calls `tt.prefetch(childHash)` immediately after `playMove` (mirroring the C++ `SearchSingleMove`), so the random-access, cache-missing TT cell the child's `find` will read is fetched while the child does its search prologue (draw checks, static eval). `prefetch` is a pure hardware hint (`prefetchAddr`: `PREFETCHT2` on amd64, `PRFM PLDL3KEEP` on arm64, no-op scalar fallback — the same three-way build-tag split as the NNUE kernels, in `engine/prefetch_*.{go,s}`); it changes no state, so the bench signature is unaffected — measured **~+2% nps** on the Ryzen 4500U.

**Evaluation** — NNUE is the only evaluator (see below); [engine/evaluate.go](engine/evaluate.go) holds the evaluator entry point and fifty-move scaling; the lockless eval cache lives in [engine/evalcache.go](engine/evalcache.go). `evaluatePosition(ss)` returns `drawScore` for insufficient-material positions, otherwise probes the eval cache and, on a miss, calls the NNUE (`searchAlphaBeta` calls `evaluatePositionNonDraw` directly at nodes whose entry check already proved no material draw) (`nnue.Network.EvaluateInt8` on the lazily-maintained accumulator, clamped by `clampEvalToBand`). Results are cached in the **lockless** `evalHashTable` (~8 MB, `evalHashTableSize` = 1<<20 entries; ported from the C++ `EvalCache`): each slot is a single `atomic.Uint64` packing the top 48 bits of the hash (a key check) and a 16-bit score, so a load/store is atomic with no torn value and no lock; a foreign/evicted entry fails the key check and reads as a miss, and racing writers are last-writer-wins. `record` clamps to ±30000 to protect the int16 field (real static evals never reach it; mate scores are never cached). Because the key checks only the hash, `clear()` must be called whenever the loaded net changes (`EnableNNUE`/`LoadNNUEFile`). The cached value is the **raw, clock-independent** eval; `scaleByRule50` (ported from the C++) is applied on the way out — never stored — scaling the static eval toward draw once the fifty-move clock passes `rule50ScaleThreshold` (20 plies) so the search has a gradient to make progress rather than shuffle a won-but-unconverted position (fixes leaks like KBN-vs-K). SEE ([engine/see.go](engine/see.go), simplified values P=100, N/B=300, R=500, Q=900) is used in move ordering (and quiescence pruning) for captures: `evaluateStaticExchange` is MakeMove-free — it applies the capture to a bitboard `seeBoard` (mirrors the C++ `EvaluateStaticExchange`), and `evaluateSwapOff` runs the least-valuable-attacker swap-off, reselecting the pawn-attacker source per ply so cross-colour pawn recaptures are counted. `TestSEECrossCheck` asserts the score bit-identical to a recursive make-move reference over ~1M captures. (The C++ `EvaluateStaticExchange` also returns a gives-check flag, computed via a `seeAttackersTo(enemyKing)` scan; Go dropped it — the flag's only consumer was a late-move-pruning guard already gated on `isQuiet()`, and the flag is set only on non-quiet moves, so the guard was **vacuous**. Removing the scan is result-neutral, +~3% nps; bench unchanged. C++ has the same vacuous flag, so parity holds. Latent gap shared with C++: quiet checking moves are *not* exempt from LMP — actually exempting them would need check detection for quiets and is a separate SPRT-gated strength experiment.) (The former handcrafted evaluator — PST tables, `pstValue`, the incremental `position.scores[c]` accumulator, pawn-structure/mobility/king-safety terms, and the material early-exit — has been removed; NNUE search behaviour is unchanged, verified by the identical `bench` node count.)

**NNUE evaluation** — the [engine/nnue/](engine/nnue/) package is the engine's only evaluator (a `*nnue.Network` on `Game`, installed by `NewGame` from the embedded net). The package is deliberately free of engine imports: positions cross the boundary as an `nnue.Board` — raw `uint64` occupancy bitboards + `uint8` piece codes. `position.nnueBoard()` in [engine/nnue_bridge.go](engine/nnue_bridge.go) (which also holds `EnableNNUE`/`LoadNNUEFile` and the search-band clamp) returns this as a **zero-copy reinterpret** — `(*nnue.Board)(unsafe.Pointer(pos))` — because `position`'s first three fields (`pieces [7]bitboard`, `colors [2]bitboard`, `squares [64]piece`) are laid out byte-identically to `nnue.Board` (`bitboard`=uint64, `piece`=uint8, same field order, mirroring the C++ `Position`). So the search hands `Update` a pointer to the live position exactly as C++ hands it a `Position const&` — no materialisation (profiling on a Ryzen 4500U showed the former per-eval value conversion was ~10% of runtime, almost all redundant parent-board rebuilds across a node's siblings; the reinterpret closed it, +~10% nps, bench bit-identical). The layout equivalence is a hard contract asserted by `TestNnueBoardLayout` (offsets + a random-position round-trip vs the explicit builder `nnueBoardExplicit`); reorder those fields and it fails loudly. It is a direct port of the C++ Pawnstar NNUE: a Chess768 → 1024 → 1 network with 8 horizontally mirrored king buckets, 8 material output heads and SCReLU activation, quantised (QA=255, QB=64, scale=400). The net is loaded from an **`RNNUE1`**-stamped `.bin` — the shared container every reckless-technology chess engine reads (the `reckless-nnue` skill is its specification): a 64-byte self-describing little-endian header, then the payload (int16 feature weights, int16 feature bias, int16 output weights, int32 output bias per output bucket). See the RNNUE1 bullet below. The shipped net is embedded via `go:embed` ([engine/nnue/embed.go](engine/nnue/embed.go), `engine/nnue/pawnstar-v20.bin` — v20, the net of release 2.0.0, trained entirely on Leela Chess Zero self-play data and the same blob byte for byte in `pawnstar` and `pawnstar-rs`; `nnue.Embedded()` parses it once). `pawnstar-v12.bin` was **removed** in 2.0.0, so there is no net in this tree at v12's shape. **Provenance and the ODbL notice:** the Leela Chess Zero self-play training data is published under the Open Database License 1.0, its contents under the Database Contents License 1.0 (`test91` 62.83% of the v20 pool, `test60` 37.17%). - **The `RNNUE1` container** (`engine/nnue/nnue.go`: `Load`, `validateArchitecture`, `Stamp`) — the shared net format, specified by the `reckless-nnue` skill, which is the authority for it; nothing here may drift from that. Little-endian: a 64-byte header (`magic` `"RNNUE1  "`, `format_version`, `header_bytes`, `features_per_bucket`, `king_buckets`, `hidden_size`, `output_buckets`, `flags`, `activation`, `qa`, `qb`, `eval_scale`, `reserved`, `king_bucket_map_crc`, `payload_bytes`, `payload_crc`, `header_crc` over bytes 0..55), then the payload bucket-major in bullet's save order. `Load` makes the two mandated checks **in order**: (1) the magic, then `header_crc`, then **every** architecture field against this build's own compile-time constants, then `king_bucket_map_crc` against the CRC of this engine's own `kingBucketMap` — the field that catches a net whose bucket *count* matches while the map's *contents* differ, which otherwise loads cleanly and reads the wrong weight bank at every eval; (2) `payload_bytes` against the bytes actually present (**exactly** — padding is no longer tolerated), then `payload_crc`. Each refusal names the field, the file's value and the engine's. `flags` bit 0 (**horizontal king mirroring**) and `output_buckets` (**material output heads**) are **build knobs**, not fixed values — see *The NNUE network shape* below. At the **default** shape they are 1 and 8, the shared architecture, and the payload is **12,617,760 bytes** (12,617,824 with the header); at v12's retained shape they are 0 and 1 and the payload is 12,582,912 + 2,048 + 4,096 + 4 = **12,589,060 bytes** (12,589,124 with the header). `format_version` is **derived from the shape**, never written down: 2 with mirroring, 1 without. A net can therefore only ever load into a build of its own shape, and a `KING_MIRRORING=0` build **refuses the shipped net naming `format_version`**, which is the container working rather than a fault. `Stamp` is `Load`'s exact inverse and writes every field from its **own** compiled constants and map, so a net stamped at one architecture can never be described as another; `TestStampReproducesEmbeddedNet` asserts it rebuilds the shipped net byte for byte.

- **The NNUE network shape** (`engine/nnue/shape_mirroring_{on,off}.go`,
  `engine/nnue/shape_heads_{eight,one}.go`) — two compile-time knobs, so **either** the shared
  architecture of the `reckless-nnue` skill or v12's older shape builds from this one tree. **The shared
  architecture is the default** as of release 2.0.0, in all three bit-exact ports at once, and is what
  the shipped net was trained for. Go has no preprocessor, so the knobs are **build tags**, and they
  name the **non-default** shape: `pawnstar_nnue_king_mirroring_off` and
  `pawnstar_nnue_output_buckets_1`, which the Makefile exposes as
  `make check KING_MIRRORING=0 OUTPUT_BUCKETS=1` and threads into every `go build`, `go test`, `go vet`
  and `go doc` as `GOTAGS`. So a build with no tags at all — a plain `go build` — is the shipped shape,
  which is the point of the polarity. The two knobs stay independent: mirroring (+14.3 Elo in zenith)
  and the eight material output heads (+14.7) were separate, separately SPRT-gated measurements.
  - **Mirroring** mirrors a perspective whose own king stands on files e-h (`square ^ 7`) before feature
    indexing, and indexes a different map: `half * 4 + min(file, 7 - file)` (per **file**) in place of
    v12's `half * 4 + file / 2` (per file-**pair**). The mirrored 64-entry map is **generated** from the
    32 half-board numbers in `kingBucketMapHalf` with bullet's own expansion arithmetic, which is the
    same 32 the trainer is handed — never two 64-entry arrays compared by eye.
  - **Output heads** are selected by `(piece_count - 2) / ceil(32 / N)`, matching bullet's
    `MaterialCount<N>`; a head is a contiguous `2 * hiddenSize` run in every output-weight
    representation, so selecting one is a slice and the SIMD kernels never learn that heads exist. The
    evaluators therefore take the **board** as well as the accumulator: the piece count is a property of
    the position, not of the accumulator.
  - **The refresh rule is the part that is silent when wrong.** A perspective may be updated
    incrementally only while its bank, its square flip **and** its colour flip all stay put. Mirroring
    adds a second way for that to fail which is not the first: on the mirrored map a king stepping
    **d1 → e1 keeps bucket 3** (files 3 and 4 both mirror to file 3) while every feature row that
    perspective reads moves. Comparing bank indices — all v12 ever needed — would diff an accumulator
    whose whole basis had just changed: no panic, no bounds error, just a wrong evaluation on about one
    king move in eight. So the three values live together in the comparable `perspective` struct and are
    compared **whole** (`nnue.NeedsRefresh`), and both failures go through one comparison.
    `TestNNUEBoundaryCrossings` crosses each boundary on purpose, compares accumulators **lane by lane**
    rather than the evaluations they produce, walks every line back as well as forward, and reports how
    many plies forced a refresh so a line that quietly stopped crossing anything cannot pass. It was
    proved by **breaking** it: narrowing the comparison to the bank alone fails ply 1 of the first line
    naming `white(bank=2304 flip=0) -> white(bank=2304 flip=7)`, while the board-half line still passes.

  irrelevant to them, since "the incremental accumulator equals a from-scratch rebuild" holds for any

- **CRC-64/XZ** (`crc64XZ`, `crcTable`) — polynomial `0x42F0E1EBA9EA3693`, reflected, init and final XOR all ones. **Go's `hash/crc64` with `crc64.ECMA` already *is* CRC-64/XZ**: `Update` complements the running value on entry and on return, so the all-ones init and final XOR are applied for you and the value it takes and returns is the post-XOR one (which is what lets it compose for streaming). Adding an init and a final XOR by hand double-complements both and gives `0x2B9C7EE4E2780C8A` for `"123456789"` where the catalogue's mandatory check value is **`0x995DC9BBDF1939FA`** — the trap, and `TestCrc64XZCheckValue` is the first thing the package proves. `TestShapeReferenceValues` pins this build's map CRC — **`0x0A20060D4E9586E0`** at the default mirrored shape, `0xCC6DDB5DAF0AB18D` at v12's `file/2` map — both byte-identical in the C++ and Rust ports.
- **A refused net is never substituted for, and the engine says which net is playing** — on a refusal `LoadNNUEFile` changes nothing: the net already loaded stays installed and goes on playing, and `handleUciSetOption` prints **two** lines on **both** streams — the loader's own refusal (naming the field, the file's value and the engine's value) and then `NNUE: keeping the net already loaded ('<kept net origin>'); '<refused path>' was refused and is not in play`, as an `info string` on stdout and bare on stderr. Both streams because a match harness keeps stderr and routinely drops `info` lines; the kept-net line because "it failed" alone leaves the operator guessing which net the games were played with, which is the whole trap (`Game.networkOrigin` remembers the installed net's origin — a path, or `embedded`). The wording is **fixed and shared by `pawnstar`, `pawnstar-rs`, `pawnstar-go` and `zenith`**, so one match log reads the same whichever engine wrote it. This replaced (2026-10-28) the earlier rule that a refusal installed `nil`: uninstalling the evaluator broke the same no-substitution rule from the other side, leaving the engine with no defined play and `bestmove 0000` at every later `go`, so an operator who missed one message got a thousand games of nothing instead of a thousand games of the previous net. `searchRootNode`'s no-net guard stays as a **defensive** path, reachable only when even the embedded net is unusable (a corrupt build — `EnableNNUE`'s failure, which is the one case that does leave no evaluator). `EnableNNUE` is still the deliberate way back to the embedded net.
- **Feature indexing** (`featureRow`): per perspective, `bucket*768 + colour*384 + (type−1)*64 + square`; the black perspective flips the colour bit and mirrors the square (`sq ^ 0x38`). King bucket per perspective from `kingBucketMap[kingSquare]` (black king mirrored first).
- **Accumulator** (`nnue.Accumulator`: two 1024-int16 perspectives) is maintained **lazily** on `searchState`. `playMove`/`makeNullMove` only mark the new ply's accumulator invalid; `undoMove` is free; `currentAccumulator` brings the current node up to date from the nearest valid ancestor (copy + incremental `update`) **only on an eval-cache miss**, so cut-off nodes and eval-cache hits never touch it. A king move crossing a bucket boundary triggers a full `refreshSide` of that perspective. Captures/EP/castling/promotion are handled uniformly via colour-bitboard diff + the `squares[]` array.
- **Output layer**: two forward passes mirror the C++ engine. `EvaluateExact` is the int16 SCReLU reference (matches the trainer/C++ to 0 cp). `EvaluateInt8` is the **search's hot-path evaluator** (`evaluatePosition` → `clampEvalToBand(EvaluateInt8(...))`): activations are requantised to uint8 (`(clamp(x,0,QA)²+256) >> int8Shift`, in [0,127]) and the output weights to int8 range (`outputWeightsI8`, derived at load by `deriveInt8OutputWeights`: `clamp(round(w/outputWScale), ±127)`); the dot then scales back by `outputWScale · 2^int8Shift` before `dequant`. Faster, at a bounded ≤40 cp deviation from `evaluateExact` (measured 40 over the 250 reference positions with the shipped v20 net, 28 with v12's) — exactly the C++ int8 layer.
- **Kernels** (all under `engine/nnue/`) are build-tag split three ways, all bit-identical: **amd64+simd** (`kernels_amd64.go`, 256-bit archsimd), **arm64** (`kernels_arm64.{go,s}`, hand-written NEON for `addColumn`/`subColumn`), and **scalar** (`kernels_generic.go` for `addColumn`/`subColumn` on other arches; the shared scalar helpers `outputDot`/`outputDotInt8`/`screlu`/`regroupWeightsForDot` live in `kernels_scalar.go`, compiled on every non-amd64-simd target including arm64 as the NEON reference). `addColumn`/`subColumn` are the accumulator column updates; `outputDot` (int16 reference) and `outputDotInt8` (int8) are the output dots. The int8 dot is the exact integer sum `Σ u8·w8` (products fit int32), so scalar == SIMD == NEON bit-for-bit.
- **The search's int8 output dot is hand-written AVX2 assembly** ([engine/nnue/dot_amd64.s](engine/nnue/dot_amd64.s), `outputDotInt8Asm`, dispatched via `Network.int8OutputDot`): a port of the C++ `OutputDotInt8Avx2` — per 32 lanes it clamps, SCReLU-squares (VPMADDWD self-multiply of the zero-extended `[v,0]` pairs), `>>9` to a uint8 activation, packs to `uint8x32` in natural order (`VPACKUSDW`×2 + `VPACKUSWB` + `VPERMD`), then `VPMADDUBSW` against the **natural-order int8 weights** (`outputWeightsI8Nat`) and widens+accumulates in int32. This exists because archsimd can't express the uint8 pack (no `uint16→uint8 ConcatGrouped`); the asm processes 32 lanes/iter (vs archsimd's 16) and is **~1.9× faster (243→129 ns, C++ parity)**, cutting `EvaluateInt8` ~249→132 ns. `TestOutputDotInt8Asm` gates it bit-identical to the archsimd int16 dot (retained as the reference) over random accumulators; scalar/non-AVX2 builds fall back to the archsimd/scalar `outputDotInt8` via `int8OutputDot` in `dot_generic.go`.
- **The arm64 int8 output dot is hand-written NEON assembly** ([engine/nnue/dot_arm64.s](engine/nnue/dot_arm64.s), also `outputDotInt8Asm`, same `int8OutputDot` dispatch): the NEON analogue of the AVX2 kernel. Per 8 int16 lanes: `SQXTUN` clamps the accumulator to unsigned [0,QA] and narrows to uint8, `UMULL` squares it to uint16, add the round (256) and an **unsigned `VUSHR` >>9** give the uint8 activation in [0,127], then `SMLAL`/`SMLAL2` signed-widen-multiply against the int8-range weights (int16, natural order — arm64 consumes `outputWeightsI8`, *not* `outputWeightsI8Nat`) into int32. Unrolled 4 blocks/iter with **four independent int32 accumulator pairs** (V16–V23) to break the loop-carried SMLAL-latency chain. Go's arm64 assembler has no vector integer multiply / dot-product mnemonic, so `SQXTUN`/`UMULL`/`SMLAL`/`SMLAL2` are emitted as `WORD $0x…` encodings (clang-derived; `go tool objdump` decodes each back to the intended instruction). Accumulator `addColumn`/`subColumn` use plain NEON `VADD`/`VSUB` (named mnemonics, no encoding). Micro-bench (Apple Silicon): `EvaluateInt8` **1242→125 ns (9.9×)**, refresh 7.6×, update 7.2×. The arm64 `TestOutputDotInt8Asm` ([engine/nnue/dot_asm_arm64_test.go](engine/nnue/dot_asm_arm64_test.go)) gates the NEON dot bit-identical to the scalar `outputDotInt8`.
- **Score band**: `EvaluateExact` keeps the faithful ±30000 clamp for the reference test; the search path clamps via the engine-side `clampEvalToBand` into ±`nnueSearchClamp` = ±(`winThreshold`−1000) = ±30000 (= C++ `kMaxEvaluation`) so a large eval stays below `winThreshold` (31000) and can never collide with mate scores (±31900).
- **Gates**: `TestNNUEReference` (int16 == C++ 250-FEN reference at 0 cp), `TestNNUEInt8` (int8 within 40 cp of int16 over the 250 FENs; also confirms scalar == SIMD), `TestNNUEIncremental` (lazy accumulator == full refresh, bit-identical). Enable per-game with `game.EnableNNUE()` (embedded) or `game.LoadNNUEFile(path)` (external).

**History heuristic** — [engine/history.go](engine/history.go) is a **butterfly table**: `counts[2][4096]` (signed `int32`) indexed by side-to-move and `move.fromTo()`, scoring how good each move has been at raising alpha or causing a beta cutoff anywhere in the tree (pooling across plies concentrates the statistics across branches and transpositions; the explicit colour dimension replaces the accidental colour proxy that per-ply indexing provided, which null-move subtrees polluted). It is updated with a **depth-weighted bonus/malus + gravity** (`recordGood` in [engine/moveorder.go](engine/moveorder.go)): a good move is credited `historyBonus(depth) = min(depth², 400)`; on a beta cutoff every *other* quiet move that was searched at the node but failed (collected in a stack-resident `quietsTried` list in `searchAlphaBeta`) is debited the same magnitude (the **malus**); and `applyGravity` (`entry += bonus − entry·|bonus|/historyMax`, `historyMax` = 16384) self-saturates each entry toward ±`historyMax` so recent evidence overwrites stale evidence. The **same bonus/malus + gravity** drives the 1-ply continuation history (`applyContinuationHistoryBonus`). Scores are added to the quiet-move sort score by `scoreAndSortMoves` (alongside continuation history). This replaced an increment-only `+1` counter (2026-07-05): **SPRT +17.2 ± 9.8 Elo at 10+0.1** (3295 games, LLR 2.96 → H1 accepted). Note it *raises* fixed-depth node counts (bench 6,888,983 → 6,601,454, BK-24 depth-12 +~11%) — a case where the standing fixed-depth node probe is a **false negative**: the extra nodes buy better move choices, which only a real time-control SPRT reveals (the probe assumes node-inflation ⟹ weaker, true for the rejected capture-history variants but not here). Quiescence stays on the plain `recordGoodMove` (`++`) increment — it has no meaningful depth. The `historyTable` lives on `searchState` (per-thread, so Lazy SMP threads don't contend); it starts fresh each search (zeroed by `resetForSearch`). The countermove and continuation-history tables are per-`searchState` too — see the Search move-ordering paragraph.

The file's own `#` header is the authority for anything written about its provenance. **Never regenerate it**: the header carries a generation timestamp, so a second run of the generator produces a different file, and there is no generator in this tree (nor should one be added) — take the bytes from `pawnstar` with `git -C ../pawnstar show origin/main:pawnstar.book > engine/book.txt`. [.gitattributes](.gitattributes) marks it `-text` so no CRLF checkout can change what `go:embed` compiles in. This replaced (2026-10-30) a 385-line book derived from TSCP's `book.txt` that was asserted to be public domain in about twenty places across the three ports: TSCP is Copyright 1997 Tom Kerrigan and the only permission ever located was an informal 2002 email allowing use "as long as you're not making any money off of it" — non-commercial, so GPL-incompatible, and not a dedication at all; because the book is embedded, every Go binary ever shipped contained those bytes. The claim was removed rather than re-worded, because no wording could have made it true. `TestShippedBookProvenance` holds the **embedded** bytes to the new claim (names Lichess, the URL, `CC0 1.0` and the dedication URL; no "TSCP", no "Kerrigan"; and more than 385 opening lines, because a book truncated to its header would load fine and play nothing). It also pins the screening: that the book carries `?` marks at all, so regenerating it with `make_book` and forgetting `filter_book` is caught rather than silently shipping every move the database offered; that the file distinguishes the engine's own moves from the database's; and that every position a line continues from still offers a selectable move, since a position whose every move is marked would silently drop the engine out of book. `loadOpeningBook` replays each line from the start position and maps Zobrist hashes to candidate next moves. The embedded book is parsed **once** (`sync.Once`) and shared read-only across games (~10 ms saved per `NewGame`); `openingBook.clear` drops a game's map reference rather than mutating the shared map. A move written with a trailing `?` is *questionable*: it is replayed so the rest of the line still parses, but is never recorded as a candidate (`getMove` will never return it) — matching the C++ book semantics. The shipped book **is** marked: `pawnstar`'s `tools/filter_book` ran that engine's own NNUE at depth 12 over it and put a `?` on every move scoring more than 100 cp below its position's best, so the engine answers a book move it would not play itself and never offers it — 922 of the 3,328 lines carry a mark. 84 positions whose every move is marked carry the engine's own choice as an extra, unmarked line, so no position the book continues from can be left with nothing playable; those 84 moves are the only ones in the file that are not the Lichess database's, and the file says so. `getMove` returns a random candidate for variety across games.

**UCI protocol** — `Game.HandleCommand` in [engine/uci.go](engine/uci.go) (the protocol layer; `Game` itself lives in [engine/game.go](engine/game.go), the chess clock in [engine/clock.go](engine/clock.go)) parses the standard UCI commands: `uci`, `isready`, `ucinewgame`, `position`, `go` (all clock types plus `ponder`, `nodes <n>` and `searchmoves ...`, whose move list ends at the next recognised `go` keyword — `goKeywords`/`isGoKeyword`, the same rule as the C++ `kCollectMoves` and the Rust `State::CollectMoves`; it used to swallow the rest of the line, so `go searchmoves e2e4 depth 10` set no depth limit at all, and `TestUCIGoSearchMovesStopsAtTheNextKeyword` now pins it), `ponderhit`, `stop`, `quit`, `setoption`, `license` (prints the engine's licence and the third-party notices the shipped data obliges - `engine/licence.go`, printing only, reads and writes no engine state; the wording is **fixed and shared by `pawnstar`, `pawnstar-rs`, `pawnstar-go` and `zenith`**, and `TestLicenceNoticeAgreesWithTheNoticesFile` holds it to `THIRD-PARTY-NOTICES.md`), and `bench` / `bench <depth>` (a node-count benchmark over the 16 positions in `benchFens` — copied verbatim from the C++ engine's `kBenchFens`, the Bratko-Kopec set — searched to `benchDepth` = 13 by default or an explicit `<depth>`, single-threaded, book-off, and on a **pinned `benchHashMB` = 64 MB** TT so the node total is a stable signature independent of the `Hash` option and comparable to the C++ default hash (64 MB) — [engine/bench.go](engine/bench.go); mirrors the C++ `handle_bench` otherwise, the hash starting empty but persisting across the positions, and restores the caller's TT on return. Current signature: **5,617,906 nodes** (since release 2.0.0's shipped net and default shape; 6,601,454 with the v12 net at v12's shape, 6,888,983 with the earlier butterfly history, 7,007,401 before that), **bit-for-bit identical to the C++ engine** (same total, and same bestmove + node count on all 16 positions), and pinned by the `benchGoldenNodes` assertion in the UCI test. The engines formerly diverged by 3,656 nodes at pos07: the C++ `MakeMove` encoded a single pawn push as `kNonCapture` and *incremented* the fifty-move clock instead of resetting it, so — the Zobrist hash excluding the clock — `ScaleByRule50` scaled a deep static eval differently, which at int8 resolution flipped one quiescence stand-pat cutoff. Fixed in the C++ engine (reset the clock on a pawn `kNonCapture`); Go was already correct via its dedicated `pawnSinglePush` move kind). Options advertised: `OwnBook` (check; false forces a real search over a book move), `EvalFile` (string; an RNNUE1 net path or `<embedded>`; a refused net is reported on stdout and stderr and the net already loaded keeps playing — see the refusal bullet under NNUE evaluation), `Threads` (spin; Lazy SMP thread count), `Hash` (spin, MB, **default `hashTableMB` = 64**, the same number the C++ and Rust ports advertise — an unequal default is an unequal collision pattern and so an unequal node count at a fixed depth; `TestUCIHandshakeInProcess` pins the exact line), `Clear Hash` (button; clears TT + eval cache), `Move Overhead` (spin, ms; reserved from every hard deadline), and `Ponder` (check; advertises pondering support). `handleUciSetOption`/`parseSetOption` span multi-word option names and values. `info` lines report `depth`, `seldepth`, `score cp`/`score mate N`, `time`, `nodes` (cumulative), `nps`, `hashfull`, and `pv`. [main.go](main.go) reads stdin line-by-line and delegates to `HandleCommand` and sets the thread count from `PAWNSTAR_THREADS`/`NumCPU` (NNUE is installed by `NewGame`).

**Pondering** — `go ponder` searches on the opponent's time. The clock is armed on the UCI goroutine by `armClock` (via `startThinking`) *before* the search goroutine starts, so the budgets are set with a happens-before to the search; the live deadline lives in two `atomic.Int64`s on `Game` (`searchStartNanos`, the soft-budget origin; `hardDeadlineNanos`, or the `noDeadlineNanos` sentinel) because `ponderhit` (UCI goroutine) mutates them mid-search while the search goroutines read them every 2048 nodes. A ponder search arms no hard deadline and the soft-budget early-exit is gated off (`!isPondering`), so it runs until `ponderhit` (→ `onPonderhit` resets the origin and arms the deadline from that moment, budget-from-ponderhit) or `stop`. `searchEntry` defers `bestmove` via a ponder-wait loop until `isPondering` clears or `stop` sets `isStopRequested` (which only the UCI goroutine writes), then emits `bestmove <m> ponder <reply>` (the reply is PV[1], `game.ponderMove`, set by the main thread's `iterativeDeepen`). Race-free by construction (the two clock words + the cancel/pondering flags are atomic); `TestPonderRace` verifies it under `-race`, and the UCI test (`uci_test.go`) checks the protocol (no `bestmove` until `ponderhit`, then a timed search).

**Stopping a search** — `isCancelPending` is cleared only by the code that starts a search, before it starts it (`startThinking` before the `go` statement; `newGameFromFen` and `runBench` for the callers that run `searchRootNode` directly) and never by a search goroutine. When `searchRootNode` cleared it as it began, a `stop` or `quit` that reached `stopThinking` before the goroutine got that far was lost, and `go infinite` + `stop` hung for ever (every attempt, through the binary); `TestUCIStopRacesInProcess` and `TestUCIStopAndQuitStraightAfterGo` hold it. The C++ and Rust engines share this design. `handleUciGo`, like `position`, `ucinewgame` and `bench`, stops a running search before it touches what that search reads (`-race` caught `go infinite` + `go depth 1` rewriting `timeControl` under the old search).

**Numeric UCI values** — `go` values, `setoption` numbers and `bench <depth>` must be whole integers (`strconv.Atoi`, the rule the C++ `ParseInteger` and the Rust `parse_integer` share). A value-taking `go` keyword whose value is missing or malformed is ignored with it (`go depth abc` and a truncated `go nodes` are a plain `go`, not a fixed-depth or unbounded search), an option is left as it was, and `bench` keeps its default depth.

**Search diagnostics** — [engine/debug.go](engine/debug.go) defines a global `dbgx debugX` struct with counters for beta cutoffs, TT hits by node type, null-move/LMR/PVS attempt and fail counts, the pruning/reduction techniques (`checkExtensions`, `iirReductions`, `rfpPrunes`, `lmpPrunes`, `qsearchSeePrunes`, `lmrAttempts1/2/3`), draw detection (`drawsByRepetition`), and killer move beta cutoffs (`killerBetaCutoffs`). The search reaches them through `searchState.dbg`: the main thread points at the global `dbgx`, helper threads at a throwaway, so the counters neither race nor contend under Lazy SMP (helper counts are discarded; `dbgxPrint` in single-threaded tests sees the full picture). Call `dbgxClear()` before a search and `dbgxPrint()` after to inspect search behaviour.
