# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build

Requires Go 1.26 or later (the NNUE SIMD kernels use the `simd/archsimd` package, gated behind `GOEXPERIMENT=simd`).

```bash
make build                  # build with GOEXPERIMENT=simd (recommended) -> ./pawnstar-go
make test                   # run all tests with SIMD enabled
make test-short             # -short variant
make baseline               # snapshot the current binary as ./pawnstar-go-baseline for SPRT
```

The `Makefile` sets `GOEXPERIMENT=simd` for you. Building directly still works — `GOEXPERIMENT=simd go build -o pawnstar-go .` — and a plain `go build` compiles too, falling back to the scalar NNUE kernels (`engine/nnue_kernels_generic.go`) selected by build tag. The SIMD and scalar kernels are bit-identical; SIMD is ~3–5× faster on the hot paths.

Run the engine interactively via UCI: `./pawnstar-go`. NNUE is the only evaluator (the embedded net is installed at construction); load an alternative net with the `EvalFile` UCI option.

## Running Tests

Move generation correctness is verified by perft tests against known node counts:

```bash
go test ./engine/ -run TestPerft -v               # all perft positions (slow — runs up to depth 6)
go test ./engine/ -run TestPerft -short -v        # quick run, caps depth at 5
go test ./engine/ -run TestPerft/002 -v           # single position by 1-based index (002 = second position)
go test ./engine/ -run TestPerftExtra -short -v  # verify incremental Zobrist hash vs recomputed hash at every node
go test ./engine/ -run TestSearch -short -v       # run search on every EPD position to depth 9
go test ./engine/ -run TestBratkoKopec -v         # 24 Bratko-Kopec positions at depth 8; search quality regression
go test ./engine/ -run TestSEE -v                 # 24 SEE unit cases + TestSEECrossCheck (fast == make-move reference over ~1M captures)
go test ./engine/ -run TestNNUEReference -v       # NNUE int16 EvaluateExact vs 250-FEN C++ reference (gate: 0 cp)
go test ./engine/ -run TestNNUEInt8 -v            # search's int8 eval within 40 cp of int16 ref (also scalar==SIMD)
go test ./engine/ -run TestNNUEIncremental -v     # lazy accumulator == full refresh, bit-identical
go test ./engine/ -run TestOpeningBook -v         # book '?' (questionable) move handling
go test ./engine/ -run 'TestArmDeadline|TestTimeControl' -v  # chess-clock deadline / defaults
make test-uci                                     # UCI protocol as a process: handshake, seldepth, searchmoves, currmove, bench determinism
go test ./engine/ -bench BenchmarkNNUE -benchmem   # NNUE evaluate/refresh/update micro-benchmarks
go test ./engine/ -bench BenchmarkPerft7 -benchtime=10s
```

Run these with `GOEXPERIMENT=simd` (or via `make test`) so the SIMD kernels are exercised. Always run `TestPerft` and `TestSearch` together when verifying engine changes. `TestBratkoKopec` is the search quality gate; it runs with **NNUE enabled** and its accepted move set was generated from multiple NNUE runs at depths 7–8 (regenerate with `GEN_BK=1 go test -run TestGenerateBratkoKopecNNUE` after swapping the embedded net). `TestNNUEReference` (int16 exact-eval correctness), `TestNNUEInt8` (the search's int8 eval vs the int16 reference, and scalar == SIMD), and `TestNNUEIncremental` (lazy accumulator correctness) are the NNUE gates — all must stay green after any accumulator or kernel change.

Perft (move generation only) runs at ~42 Mnps; the NNUE eval used in real search is slower per node but far stronger (when first ported: SPRT +572 Elo vs the engine's former handcrafted eval at fixed depth, since removed). The C++ original reaches ~700 Mnps via BMI2 PEXT. Perft benchmarks are the primary tool for tracking move-generation performance regressions. In real NNUE search the Go↔C++ speed gap is far smaller than the raw move-gen gap, because search nps is dominated by evaluation (where the SIMD kernels are close to the C++ hot path): over the 24 Bratko-Kopec positions at depth 10, single-threaded with bit-identical trees, the Go engine runs ~1.06 Mnps against the C++ engine's ~1.77 Mnps — **~1.66× slower** (measured by interleaving the two engines per position across several rounds; stable 1.58–1.74).

## SPRT self-play harness

`tools/sprt.sh <candidate-bin> <baseline-bin> [rounds]` runs a fastchess binary-vs-binary SPRT (single-core engines via `GOMAXPROCS=1`, fixed depth via `DEPTH=`, openings from `~/pawnstar_nnue/openings.epd`). Snapshot a baseline with `make baseline`. Every eval or search change that could affect strength is gated this way — run it in the background, they are long. The NNUE port itself passed [0, 10] with LLR 2.96 (146W/3L/5D over 154 games).

## Known Pitfalls

**Promotion notation** — `move.String()` outputs correct UCI notation (`e7e8q`). `move.GoString()` outputs a human-readable debug form (`pe7e8=q`) that is **not** UCI and must never be used for engine communication.

**`noSquare` equals a1** — `noSquare` is defined as `square(0)`, which is the same integer value as `a1`. It is only used for the en-passant target square and castling sentinel contexts where `a1` would never validly appear.

**`ucinewgame` does not clear the TT/eval cache** — `newGameFromFen` (called on `ucinewgame`) resets only the position stack, node count, cancel flag and clock; the transposition table and eval cache **persist** (only the `Clear Hash` button clears them, in `HandleCommand`). This is deliberate — you want the TT to carry across moves within a game — but it diverges from the C++ engine, which clears on `ucinewgame`. The consequence for tooling: repeating the *same* position via `ucinewgame` + `go depth N` in one persistent UCI session gives **non-deterministic, shrinking** node counts as the stale TT is reused. To reproduce the deterministic BK node counts in a persistent session, send `setoption name Clear Hash` before each search (or start a fresh process per position). The in-repo tests are unaffected — they build a fresh `Game` per position.

## Architecture

Pawnstar-Go is a UCI chess engine using bitboard board representation and alpha-beta search. It is a port of the C++ Pawnstar engine.

**Board representation** — `position` ([engine/position.go](engine/position.go)) is a value type used with copy-make traversal: `makeMove` and `makeNullMove` operate on a caller-owned copy of the struct. `Game.posStack []position` (heap-allocated, capacity 512) maintains the history stack; undoing a move is a slice truncation. The struct holds `pieces [7]bitboard` (indexed by piece type constant, `pawn`=1…`king`=6; index 0 (`noPiece`) holds the **occupied-squares** bitboard, maintained incrementally so `occupied()` is a plain load — mirrors the C++ `pieces_[kNone]`) and `colors [2]bitboard` (indexed by color constant, `white`=0/`black`=1) instead of named per-piece fields, plus a `squares [64]piece` array for O(1) lookup, an incremental Zobrist hash, `colorToMove color`, and `halfMove uint8` (50-move clock). The king square is not stored; `kingSquare(c color) square` computes it on demand as `(pieces[king] & colors[c]).lsb()`. `positionFromFen` constructs a `position` from a FEN string and treats `'0'` as a no-op digit (advance by 0 squares) to handle non-standard FEN notation. `bitboard` ([engine/bitboard.go](engine/bitboard.go)) is a `uint64` with methods for all set operations.

**Move encoding** — `move` ([engine/move.go](engine/move.go)) is a packed `int64` with an identical bit layout to the C++ version:

```
bits  0– 5  to square
bits  6–11  from square
bits 12–14  moving piece
bits 15–17  captured piece
bits 18–21  move type
bit     22  gives-check flag
bits 23–24  transposition node type (nodeType)
bits 25–32  transposition depth searched (int8)
bits 33–40  transposition age / generation (uint8)
bits 41–63  score (signed 23-bit)
```

Bits 23–63 are dual-purpose: during move ordering they hold a sort score (`move.withScore`/`move.score`, bits 41–63), and inside a transposition entry they hold the packed `{score, depth, nodeType, age}` metadata (`move.withTTData`/`setTTAge` plus the `ttDepth`/`ttNodeType`/`ttAge` accessors). A move is never both at once, so the spare bits are shared — this is what lets a TT cell be exactly two 64-bit words (see the lockless table below). The score is signed 23-bit; every move-ordering score and stored search score fits. `move.bits()`/`moveFromBits` convert to/from the raw `uint64`. Move lists are `[]move` slices with `make([]move, 0, 64)`. `move.equal`/`isNone` mask to the identity bits (0–21), so metadata never affects identity.

**Attack generation** — [engine/tables.go](engine/tables.go) initialises all precomputed data in its `init()` function: magic bitboard tables for sliding pieces (`bishopAttacks`, `rookAttacks` — magic numbers found offline with seed 1337), ray tables (eight directions × 64 squares), knight/king/pawn attack tables, pawn structure masks, king pawn shelter masks, intervening-square tables, and Zobrist hashes (seeded 1968). `computePins` ([engine/pins.go](engine/pins.go)) identifies absolutely pinned pieces and their allowed ray before move generation.

**Move generation** — [engine/movegen.go](engine/movegen.go) implements fully legal move generation. `generateLegalMoves` and `generateLegalCaptures` are the entry points. Internally, `generateMoves` builds the king's forbidden-square set (with X-ray attacks through the king), handles double-check early return, restricts non-king moves to checker capture or interposition in single check, applies pin constraints via `pins.allowedSquares`, generates castling, and generates all pawn move types inline (including en-passant with a horizontal discovered-check test).

**Search** — `Game` ([engine/game.go](engine/game.go)) owns the lockless transposition table and eval cache (shared by all threads), the chess clock, opening book, position history stack, and `threadCount` (Lazy SMP thread count; default 1, raised by `main()` from `PAWNSTAR_THREADS`/`NumCPU` or the UCI `Threads` option). `isCancelPending` is an `atomic.Bool`. `startThinking` launches the search on one goroutine (so UCI can still process `stop`); `stopThinking` stores `true` into `isCancelPending` then blocks on a `sync.WaitGroup`.

**Lazy SMP** (ported from the C++ engine): `searchRootNode` launches `threadCount − 1` helper goroutines and runs the main thread itself. Each thread runs `iterativeDeepen` — an independent iterative-deepening search of the whole root — with its **own `searchState`**; helpers get a private throwaway diagnostics struct and their own copy of the root move list. The **main thread (id 0) is authoritative**: it prints `info`, applies time management, and returns the move. Helper threads (id ≥ 1) stay silent and follow the Stockfish-style iteration-skip schedule (`lazySmpSkipSize`/`lazySmpSkipPhase`) so they desynchronise and prefill the shared TT with diverse entries. When the main thread finishes it sets `isCancelPending` and joins the helpers.

All recursive search functions ([engine/search.go](engine/search.go)) take `*searchState`. **Everything on `searchState` is per-thread** — `posStack`, `hashStack`, `killers`, `history` (moved off `Game` so threads don't contend), continuation history, countermoves, the NNUE accumulator stack, `nodeCount`, and the `dbg *debugX` (the global `dbgx` for the main thread, a throwaway per helper). Only the lockless TT + eval cache, the read-only time control, and the atomic cancel flag are shared, so the concurrent search is data-race free with no locks. `newSearchStateFromGame` builds `hashStack` from the full game history and seeds `posStack` with the current position.

`searchRootNode` drives iterative deepening from `startDepth` (3). Each depth iteration is a single **full-window** root pass (`[initialAlpha, initialBeta]`): `alpha` starts at the minimum and is raised as root moves improve, so PVS null-windows every move after the first — there is **no aspiration window** (the C++ engine tested and rejected aspiration; a cross-engine BK diff at fixed depth confirmed aspiration was the largest Go↔C++ divergence, so Go dropped it to match). With aspiration removed plus Zobrist parity (shared `xorshift64star`), score-scale parity (§ Evaluation below), the per-move null-window fix (§ `searchAlphaBeta` below), and the PV-capture fix (§ Principal variation below), **all 24 Bratko-Kopec positions match the C++ engine bit-for-bit at fixed depth — identical bestmove, score, cumulative node count, and full principal variation** (single-threaded, book off; verified at depth 8 and depth 10). This is the standing faithfulness gate. Early-exit heuristics apply on the Standard clock when the best move and/or score are stable across depths.

`searchAlphaBeta` implements PVS plus the pruning/reduction stack ported from the C++ Pawnstar (margins in [engine/constants.go](engine/constants.go); they carry over because the NNUE eval is the same centipawn scale): internal iterative reduction (−1 ply when there is no TT move at depth ≥ `noTTReduceMinDepth`), and — at non-PV non-check nodes, using a static eval computed once — reverse futility pruning (`eval − rfpMargin·depth ≥ beta`) and null-move pruning (R=4, gated on `eval ≥ beta`). In the move loop: late move pruning (skip quiet moves once `moveIdx ≥ lmpBase + depth²` at depth ≤ `lmpMaxDepth`) and LMR (any late move at null-window non-check nodes: −1 at idx > 3, −2 at idx > 6 & depth > 3, −3 additionally with zero history), re-searched at full depth on a fail-high. The **null-window predicate (`beta == alpha+1`) is recomputed per move against the current alpha, not precomputed once** — at a PV node, once an earlier move raises alpha to `beta−1` the remaining moves are effectively a null-window search and LMP/LMR must engage for them; this mirrors the C++ inline check and is required for bit-identical search (a precomputed flag left the last two BK positions diverging). Quiescence adds SEE pruning (stop at the first losing capture). A node in check is extended one ply (check extension) and its evasions are searched; quiescence re-enters `searchAlphaBeta` when in check. The pruning/reduction stack was worth +183 Elo (SPRT, 10+0.1); the check extension plus the countermove/continuation-history move ordering a further +160 Elo; Lazy SMP adds parallel scaling on top (4 threads ≈ +160 Elo vs 1 at 10+0.1).

**Principal variation** — the PV (a `variation` = `[]move`) is captured **at the moment a move raises alpha** and nowhere else: `copyVariation(parentPV, pv, move)` sets `parentPV = move ++ child.pv` both in the TT-move block and in the main move loop. There is deliberately **no post-loop re-copy** — after the best move, later siblings run `pv.clear()` then fail low, so by the end of the loop `pv` no longer holds the best move's line; re-copying there (an earlier Go bug) truncated the PV to ~2 plies. Removing that re-copy and adding the missing TT-move capture makes the full PV bit-identical to C++ (matches `SearchState::SearchAlphaBeta`, whose end-of-loop comment notes "parent_pv was already set … at the alpha-raise above"). `iterativeDeepen` captures the root PV the same way and publishes `ponderMove` = PV[1].

Move ordering (`searchState.scoreAndSortMoves`, a banded scheme ported from the C++ `ScoreAndSortMoves`): (1) TT move tried first; (2) remaining moves scored into disjoint bands — winning captures/promotions `winningCaptureBase + SEE` on top, then the two killers, then the countermove to the previous move (`countermoveScore`), then quiet moves by `history + continuationHistory` clamped to `maxQuietScore`; losing captures score by their negative SEE and sink below the quiet moves. `prevMove` (the move played at the parent) keys the countermove and continuation-history heuristics. On a good move, `recordGood` credits the main history and continuation history; a quiet beta cutoff additionally updates killers (`updateKillers`, now all quiet moves) and the countermove. The countermove table (`[contKeys]move`, keyed by `prevMove.pieceTo()`) and the 1-ply continuation history (`[]int16`, keyed by `[prev.pieceTo()][move.pieceTo()]`, saturating) live on `searchState` and persist across a search. Sorting is `sortMoves` — a **stable in-place insertion sort** by descending score, used at every node and the root (mirrors the C++ `SortMoves`); a move list is small and hard-bounded, so insertion sort beats an O(n log n) sort with a scratch buffer, and stability makes equal-score move choices deterministic.

**Transposition table** — Single table ([engine/transposition.go](engine/transposition.go)), sized from `hashTableMB` and rounded up to a power of two so entries index with `hash & mask`. **Lockless via Hyatt's XOR trick** (ported from the C++ engine): each 16-byte cell is two `atomic.Uint64` words — `data` (the packed move, carrying score/depth/nodeType/age in its spare bits) and `key = hash ^ data`. `find` loads both words with relaxed atomics and accepts the cell only when `key ^ data == hash`; a torn pair left by two concurrent stores (key from one, data from another) fails that check and reads as a miss, and the same reconstruction doubles as the full-hash collision guard. So there are no per-entry locks: workers read/write freely, racing writers resolve to a benign last-writer-wins, and a torn read costs at most a spurious miss (re-search) — never a wrong move or garbage score. Per-word atomicity keeps each word itself tear-free (and the race detector quiet); the XOR key supplies the cross-word consistency. Replacement policy (in `record`): overwrite when the slot is empty, the existing entry is from an older generation (`cur.ttAge() != currentAge`), the new depth is ≥ the stored depth, or the new node is PV. `age()` bumps `currentAge` (O(1), wraps at 256) at the start of each root search; `record` stamps it via `setTTAge`. The `transposition` value returned by `find` is `{hash, move}` with `score()`/`depth()`/`nodeType()`/`age()` reading straight out of the packed move.

**Evaluation** — NNUE is the only evaluator (see below); [engine/evaluate.go](engine/evaluate.go) now holds just the shared, evaluator-independent machinery. `evaluatePosition(ss)` returns `drawScore` for insufficient-material positions, otherwise probes the eval cache and, on a miss, calls the NNUE (`nnue.searchEvalAcc` on the lazily-maintained accumulator). Results are cached in the **lockless** `evalHashTable` (~8 MB, `evalHashTableSize` = 1<<20 entries; ported from the C++ `EvalCache`): each slot is a single `atomic.Uint64` packing the top 48 bits of the hash (a key check) and a 16-bit score, so a load/store is atomic with no torn value and no lock; a foreign/evicted entry fails the key check and reads as a miss, and racing writers are last-writer-wins. `record` clamps to ±30000 to protect the int16 field (real static evals never reach it; mate scores are never cached). Because the key checks only the hash, `clear()` must be called whenever the loaded net changes (`EnableNNUE`/`LoadNNUEFile`). The cached value is the **raw, clock-independent** eval; `scaleByRule50` (ported from the C++) is applied on the way out — never stored — scaling the static eval toward draw once the fifty-move clock passes `rule50ScaleThreshold` (20 plies) so the search has a gradient to make progress rather than shuffle a won-but-unconverted position (fixes leaks like KBN-vs-K). SEE ([engine/see.go](engine/see.go), simplified values P=100, N/B=300, R=500, Q=900) is used in move ordering (and quiescence pruning) for captures: `evaluateStaticExchange` is MakeMove-free — it applies the capture to a bitboard `seeBoard` and detects check with `seeAttackersTo` (mirrors the C++ `EvaluateStaticExchange`), and `evaluateSwapOff` runs the least-valuable-attacker swap-off, reselecting the pawn-attacker source per ply so cross-colour pawn recaptures are counted. `TestSEECrossCheck` asserts it bit-identical to a recursive make-move reference over ~1M captures. (The former handcrafted evaluator — PST tables, `pstValue`, the incremental `position.scores[c]` accumulator, pawn-structure/mobility/king-safety terms, and the material early-exit — has been removed; NNUE search behaviour is unchanged, verified by the identical `bench` node count.)

**NNUE evaluation** — [engine/nnue.go](engine/nnue.go) is the engine's only evaluator (a `*nnueNetwork` on `Game`, installed by `NewGame` from the embedded net). It is a direct port of the C++ Pawnstar NNUE: a Chess768 → 1024 → 1 network with 8 king buckets and SCReLU activation, quantised (QA=255, QB=64, scale=400). The net is loaded from a 32-byte `PSN1`-stamped `.bin` (little-endian int16 arrays: feature weights, feature bias, output weights, output bias) — the exact C++ `pawnstar-*.bin` format, read directly with no conversion. The v12 net is embedded via `go:embed` ([engine/nnue_embed.go](engine/nnue_embed.go), `engine/nnue/pawnstar-v12.bin`).

- **Feature indexing** (`nnueFeatureRow`): per perspective, `bucket*768 + colour*384 + (type−1)*64 + square`; the black perspective flips the colour bit and mirrors the square (`sq ^ 0x38`). King bucket per perspective from `nnueKingBucketMap[kingSquare]` (black king mirrored first).
- **Accumulator** (`nnueAccumulator`: two 1024-int16 perspectives) is maintained **lazily** on `searchState`. `playMove`/`makeNullMove` only mark the new ply's accumulator invalid; `undoMove` is free; `currentAccumulator` brings the current node up to date from the nearest valid ancestor (copy + incremental `update`) **only on an eval-cache miss**, so cut-off nodes and eval-cache hits never touch it. A king move crossing a bucket boundary triggers a full `refreshSide` of that perspective. Captures/EP/castling/promotion are handled uniformly via colour-bitboard diff + the `squares[]` array.
- **Output layer**: two forward passes mirror the C++ engine. `evaluateExact` is the int16 SCReLU reference (matches the trainer/C++ to 0 cp). `evaluateInt8` is the **search's hot-path evaluator** (`searchEvalAcc` → `evaluateInt8`): activations are requantised to uint8 (`(clamp(x,0,QA)²+256) >> nnueInt8Shift`, in [0,127]) and the output weights to int8 range (`outputWeightsI8`, derived at load by `deriveInt8OutputWeights`: `clamp(round(w/outputWScale), ±127)`); the dot then scales back by `outputWScale · 2^nnueInt8Shift` before `nnueDequant`. Faster, at a bounded ≤40 cp (measured 28) deviation from `evaluateExact` — exactly the C++ int8 layer.
- **Kernels** are build-tag split: SIMD (`nnue_kernels_amd64.go`, `amd64 && goexperiment.simd`, 256-bit archsimd) and scalar (`nnue_kernels_generic.go`); bit-identical. `outputDot` (int16 reference) and `outputDotInt8` (search) are the output dots; `addColumn`/`subColumn` are the accumulator column updates. The int8 dot is the exact integer sum `Σ u8·w8` (products fit int32), so scalar == SIMD bit-for-bit.
- **Score band**: `evaluateExact` keeps the faithful ±30000 clamp for the reference test; the search path (`searchEvalAcc`) clamps into ±`nnueSearchClamp` = ±(`winThreshold`−1000) = ±30000 (= C++ `kMaxEvaluation`) so a large eval stays below `winThreshold` (31000) and can never collide with mate scores (±31900).
- **Gates**: `TestNNUEReference` (int16 == C++ 250-FEN reference at 0 cp), `TestNNUEInt8` (int8 within 40 cp of int16 over the 250 FENs; also confirms scalar == SIMD), `TestNNUEIncremental` (lazy accumulator == full refresh, bit-identical). Enable per-game with `game.EnableNNUE()` (embedded) or `game.LoadNNUEFile(path)` (external).

**History heuristic** — [engine/history.go](engine/history.go) records how often each (ply, from→to) pair raised alpha or caused a beta cutoff. Counts are added to the quiet-move sort score by `scoreAndSortMoves` (alongside continuation history). The `historyTable` lives on `searchState` (per-thread, so Lazy SMP threads don't contend); it starts fresh each search because a new `searchState` is built per search. The countermove and continuation-history tables are per-`searchState` too — see the Search move-ordering paragraph.

**Opening book** — [engine/book.go](engine/book.go) parses [engine/book.txt](engine/book.txt) (385 lines from TSCP — a byte-for-byte copy of the C++ engine's `pawnstar.book`, including its questionable-move markers), embedded in the binary via `go:embed` ([engine/book_embed.go](engine/book_embed.go)) so the engine always has a book with no external file to ship. `loadOpeningBook` replays each line from the start position and maps Zobrist hashes to candidate next moves. A move written with a trailing `?` is *questionable*: it is replayed so the rest of the line still parses, but is never recorded as a candidate (`getMove` will never return it) — matching the C++ book semantics (109 lines carry `?`, filtering 122 candidate entries). `getMove` returns a random candidate for variety across games.

**UCI protocol** — `Game.HandleCommand` in [engine/game.go](engine/game.go) parses the standard UCI commands: `uci`, `isready`, `ucinewgame`, `position`, `go` (all clock types plus `ponder`, `nodes <n>` and `searchmoves ...`), `ponderhit`, `stop`, `quit`, `setoption`, and `bench` (a fixed-position depth-`benchDepth` node-count benchmark, single-threaded and book-off so it is deterministic — [engine/bench.go](engine/bench.go)). Options advertised: `OwnBook` (check; false forces a real search over a book move), `EvalFile` (string; a PSN1 net path or `<embedded>`), `Threads` (spin; Lazy SMP thread count), `Hash` (spin, MB; resizes the TT), `Clear Hash` (button; clears TT + eval cache), `Move Overhead` (spin, ms; reserved from every hard deadline), and `Ponder` (check; advertises pondering support). `handleUciSetOption`/`parseSetOption` span multi-word option names and values. `info` lines report `depth`, `seldepth`, `score cp`/`score mate N`, `time`, `nodes` (cumulative), `nps`, `hashfull`, and `pv`. [main.go](main.go) reads stdin line-by-line and delegates to `HandleCommand` and sets the thread count from `PAWNSTAR_THREADS`/`NumCPU` (NNUE is installed by `NewGame`).

**Pondering** — `go ponder` searches on the opponent's time. The clock is armed on the UCI goroutine by `armClock` (via `startThinking`) *before* the search goroutine starts, so the budgets are set with a happens-before to the search; the live deadline lives in two `atomic.Int64`s on `Game` (`searchStartNanos`, the soft-budget origin; `hardDeadlineNanos`, or the `noDeadlineNanos` sentinel) because `ponderhit` (UCI goroutine) mutates them mid-search while the search goroutines read them every 2048 nodes. A ponder search arms no hard deadline and the soft-budget early-exit is gated off (`!isPondering`), so it runs until `ponderhit` (→ `onPonderhit` resets the origin and arms the deadline from that moment, budget-from-ponderhit) or `stop`. `searchEntry` defers `bestmove` via a ponder-wait loop until `isPondering` clears or the cancel flag is set, then emits `bestmove <m> ponder <reply>` (the reply is PV[1], `game.ponderMove`, set by the main thread's `iterativeDeepen`). Race-free by construction (the two clock words + the cancel/pondering flags are atomic); `TestPonderRace` verifies it under `-race`, and `test/uci_test.sh` checks the protocol (no `bestmove` until `ponderhit`, then a timed search).

**Search diagnostics** — [engine/debug.go](engine/debug.go) defines a global `dbgx debugX` struct with counters for beta cutoffs, TT hits by node type, null-move/LMR/PVS attempt and fail counts, the pruning/reduction techniques (`checkExtensions`, `iirReductions`, `rfpPrunes`, `lmpPrunes`, `qsearchSeePrunes`, `lmrAttempts1/2/3`), draw detection (`drawsByRepetition`), and killer move beta cutoffs (`killerBetaCutoffs`). The search reaches them through `searchState.dbg`: the main thread points at the global `dbgx`, helper threads at a throwaway, so the counters neither race nor contend under Lazy SMP (helper counts are discarded; `dbgxPrint` in single-threaded tests sees the full picture). Call `dbgxClear()` before a search and `dbgxPrint()` after to inspect search behaviour.
